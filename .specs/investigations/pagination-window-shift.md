# Краткий итог

Клиент ожидал прочитать 12 записей за четыре страницы по три. ID 10 повторился, потому что при вставке перед ним его позиция сдвигается с третьей на четвёртую, а следующий GET пропускает первые три строки уже изменившейся выдачи (OFFSET=page×size). При одной вставке и без дальнейших изменений страницы получаются такими: 12,11,10 → 10,9,8 → 7,6,5 → 4,3,2. ID 1 не удаляется: он оказывается на пятой странице (page=4); одно из 12 прочитанных мест занял повтор ID 10.

Этот механизм подтверждён кодом и отдельным экспериментом пользователя: GET вернул 12,11,10 и totalElements=12; POST создал ID 13 с более поздним recordedAt; следующий GET вернул 10,9,8 и totalElements=13. До вставки локальные GET показывали страницы без пересечения и различные recordedAt. Страницы 2–4 после вставки отдельно не запрашивались: положение ID 1 — расчётное следствие механизма, а не наблюдавшийся HTTP-ответ.

Для исходного случая с отметками 10:02 не хватает ответа исторического POST, подтверждения окружения/видимости вставки и полных ответов четырёх страниц. Поэтому механизм воспроизведён, но причина именно старого случая окончательно не доказана. Следующий шаг — получить эти исторические свидетельства; повторять POST не требуется. Вопрос о гарантии обхода без повторов при новых событиях остаётся владельцу контракта: сейчас такой гарантии в спецификации нет.

### Возможные причины

1. **Изменение набора между выборками:** новая запись перед ID 10 сдвигает границу страниц. Подтверждено для эксперимента пользователя; наиболее поддержанное объяснение исторического случая.
2. **Ошибка расчёта OFFSET:** например, вторая страница пропускает две строки вместо трёх. В прочитанном коде OFFSET=1×3=3; до вставки фактическая вторая страница равна 9,8,7. Постоянная ошибка смещения не объясняет проверенное локальное поведение; историческая версия процесса неизвестна.
3. **Перестановка строк с одинаковым recordedAt:** возможна при сортировке без второго ключа. В локальном наборе совпадений не обнаружено; доказательство и отдельный риск приведены ниже.
4. **Разные фильтры, базы или версии сервиса:** могли дать пересекающиеся наборы разного размера. Для исторических запросов не исключено. Эксперимент пользователя выполнен последовательно против одного base URL без дополнительных фильтров; идентичность версии процесса отдельно не проверялась.

## Фактический результат или препятствие

### Доказательство против правдоподобной альтернативы

Альтернатива: ID 10 повторился из-за перестановки строк с одинаковыми recordedAt. Агент выполнил GET page=0&size=200 на http://127.0.0.1:8080/api/v1/audit-events, HTTP 200. В 2026-11-06T12:47:23.0770990+00:00 получены все 12 записей, totalElements=12; группировка по recordedAt не обнаружила совпадений.

Времена: ID 1 — 2026-04-20T09:00:00Z, далее шаг 5 минут; ID 10 — 09:45:00Z, ID 11 — 09:50:00Z, ID 12 — 09:55:00Z той же даты. В эксперименте новая запись ID 13 получила отдельное, более позднее время. Следовательно, равные времена не нужны для воспроизведённого повтора и не объясняют его на проверенных данных. Исторический набор не представлен полностью, поэтому для него эта альтернатива не исключена. Кроме того, одна перестановка неизменного набора не объясняет рост totalElements.

### Подтверждение вставки в отдельном HTTP-эксперименте

Источник — полный вывод команд WSL, предоставленный пользователем. Все три запроса выполнены последовательно против одного адреса http://127.0.0.1:8080/api/v1/audit-events.

| Шаг | Фактический ответ |
| --- | --- |
| GET page=0&size=3 | HTTP 200; IDs 12,11,10; totalElements=12 |
| POST: actor=pagination-probe, action=LOGIN, outcome=ALLOWED | HTTP 201; ID 13; recordedAt=2026-11-06T12:53:45.952536661Z |
| GET page=1&size=3 | HTTP 200; IDs 10,9,8; totalElements=13 |

Новая запись новее ID 12, поэтому занимает начало выдачи. ID 10 сдвигается на четвёртую позицию и повторяется после OFFSET 3. В эксперименте подтверждена вставка как механизм повтора. Выход ID 1 на пятую страницу рассчитан при условии отсутствия дальнейших изменений; HTTP-проверки страниц 2–4 не было.

Историческое препятствие: нет ответа POST 10:02:15.890 и подтверждения того, какая запись стала видна между исходными выборками. recordedAt назначается до INSERT и не заменяет время commit. Отдельные SELECT content и count при BEGIN READ ONLY без явно заданного уровня изоляции не позволяют по одному totalElements восстановить точный момент вставки.

### Отдельный риск: одинаковые recordedAt

SQL сортирует только по recorded_at DESC. Если у нескольких событий время совпадёт, порядок внутри этой группы не задан; при разных запросах возможны пересечения или пропуски на границе страниц даже без вставки. Это самостоятельный риск, а не установленная причина воспроизведённого случая: на проверенных данных времена различаются.

Дополнительный уникальный ключ сортировки мог бы сделать порядок равных времён однозначным, но сам по себе не устранил бы сдвиг OFFSET при вставке перед уже прочитанными строками. Изменения реализации и контракта в рамках расследования не выбирались.

Агент выполнял чтение кода, модель и GET; POST выполнил пользователь. ID 13 сохраняется в append-only базе. Код, тесты и миграции не изменялись; сборка, тесты, прямые БД-проверки и коммит не выполнялись.

В переписке материалы не подписаны A/B; соответствие букв не установлено. Последовательно предоставленные свидетельства добавили:

- Лог: 10:02:14.120 — страница 12,11,10, totalElements=12; 10:02:17.440 — страница 10,9,8, totalElements=13. Рост количества усилил версию вставки и показал недостаточность одной перестановки равных времён для объяснения всего наблюдения.

Для доказательства причины старого случая следующий шаг остаётся прежним: получить исторический ответ POST и связать его с выборками GET. Если данных нет, остановиться на этой границе доказанного. Владелец контракта отдельно решает, нужен ли обход без повторов при новых событиях.
